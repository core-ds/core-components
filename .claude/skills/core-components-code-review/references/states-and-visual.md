# Состояния компонента, controlled/uncontrolled, visual/layout regression

## Чек-лист состояний компонента

Определяй релевантные состояния по props изменённого компонента (`typings.ts`/`Component.tsx`), а не по общему шаблону — не каждый компонент имеет все состояния ниже:

- `default` / `hover` / `active` — базовые визуальные состояния интерактивного элемента;
- `focus` (в т.ч. keyboard-only focus) — см. `references/accessibility-interaction.md`;
- `disabled` — компонент не должен реагировать на interaction (click/keyboard), обычно визуально приглушён;
- `loading` — часто взаимодействует с `disabled` (нельзя submit во время загрузки) и требует индикации (spinner/skeleton);
- `error`/`invalid` — визуальная индикация + (если применимо) `aria-invalid`/связанное сообщение об ошибке;
- `selected`/`checked`/`expanded` — состояние выбора/раскрытия, обычно управляется через controlled/uncontrolled props (см. ниже);
- `readonly` — отличается от `disabled`: значение видно и доступно для копирования/фокуса, но не редактируется;
- `empty`/`placeholder` — состояние без значения.

Если PR меняет один компонент, но не проверяет **комбинации** состояний (например, `disabled` + `error`, `loading` + `disabled`) — это частый источник визуальных/поведенческих багов, особенно если у одного из состояний более высокий приоритет в стилях/логике, чем у другого.

## Controlled/uncontrolled

В проекте встречаются два разных паттерна — важно понимать, какой из них уже применяет затронутый компонент, и не смешивать их.

### Паттерн 1: полноценный dual-mode (например, `accordion`)

```tsx
// packages/accordion/src/Component.tsx
const uncontrolled = expanded === undefined;
const [expandedState, setExpanded] = useState(uncontrolled ? defaultExpanded : expanded);
const isExpanded = uncontrolled ? expandedState : expanded;

const handleExpandedChange = useCallback(() => {
    if (uncontrolled) {
        setExpanded(!isExpanded);
    }
    onExpandedChange?.(!isExpanded);
}, [isExpanded, onExpandedChange, uncontrolled]);
```

Ключевые инварианты этого паттерна, которые стоит проверять при ревью похожего кода:

- режим определяется **отсутствием** контролирующего prop (`expanded === undefined`), а не отдельным булевым флагом типа `controlled?: boolean`;
- `defaultExpanded` задаёт только **начальное** значение (аргумент `useState`) — он не должен реагировать на изменения извне после первого рендера;
- `setExpanded` вызывается **только** в uncontrolled-ветке — если внутреннее состояние обновляется независимо от режима, controlled-режим перестаёт быть источником истины (родитель передаёт `expanded`, но компонент визуально всё равно переключается сам) — это finding;
- callback (`onExpandedChange`) вызывается **в обоих режимах** одинаково — если он вызывается только в uncontrolled-ветке, controlled-потребитель не узнает об попытке взаимодействия.

### Паттерн 2: controlled-only (например, `checkbox`)

```tsx
// packages/checkbox/src/Component.tsx
const handleChange = (event: ChangeEvent<HTMLInputElement>) => {
    if (onChange) {
        onChange(event, { checked: event.target.checked, name });
    }
};
// checked используется напрямую для рендера, внутреннего useState для него нет
```

`Checkbox` не поддерживает uncontrolled-режим вообще (нет `defaultChecked`, нет внутреннего state) — `checked` рендерится напрямую из props, `onChange` только сообщает о попытке изменения. Источник истины — исключительно родитель.

Если diff добавляет такому компоненту внутренний `useState`, дублирующий переданный controlled-prop (например, "чтобы чекбокс визуально переключался сразу, не дожидаясь родителя") — это создаёт рассинхронизацию между внутренним и внешним состоянием и обычно баг, а не улучшение отзывчивости.

### Общий чек-лист для controlled/uncontrolled diff'ов

- определи, какой из двух паттернов уже использует компонент (или должен использовать, если паттерн вводится впервые), и проверяй изменение на согласованность именно с ним;
- callback (`onChange`/`onExpandedChange`/аналог) должен вызываться независимо от режима;
- в controlled-режиме компонент не должен молча менять видимое состояние в обход переданного prop;
- смена состояния снаружи (родитель передал новое значение controlled-prop) должна корректно перерисовывать компонент.

## Отличие intentional visual change от regression

Сам факт изменённого скриншота — **не доказательство ошибки**. Прежде чем создавать finding по visual diff:

- проверь, соответствует ли изменение описанию/цели PR (visual PR, ребрендинг, дизайн-фикс — изменение снапшота ожидаемо);
- проверь, есть ли в diff соответствующее изменение исходного кода (CSS/JSX), объясняющее визуальное отличие — обновлённый `__image_snapshots__/*.png` **без** какого-либо сопутствующего изменения кода компонента подозрителен (либо flaky-обновление, либо непреднамеренный побочный эффект от изменения в общем модуле/теме);
- и наоборот: изменение CSS/layout компонента **без** обновления скриншот-тестов — потенциально непротестированное визуально изменение (см. tests-and-conventions.md про покрытие).

## Скриншот-тесты проекта (`docs/screenshots.stories.mdx`)

- Два вида: **статические** (`generateTestCases`/`createSpriteStorybookUrl` — комбинации props/knobs, один скриншот на комбинацию) и **динамические** (playwright взаимодействие — клик/ввод — затем скриншот).
- Снапшоты хранятся в git-lfs (`packages/<name>/src/__image_snapshots__/*.png`). **В текстовом diff PR такой файл выглядит как изменение LFS-pointer'а** (`oid sha256:...`, `size ...`) — сам diff не показывает визуальное отличие, только факт того, что снапшот обновлён. Не пытайся оценить характер визуального изменения по тексту pointer-диффа — либо посмотри на реальные PNG (если доступны через CI/артефакты), либо опирайся на описание PR и changeset, либо явно пометь вывод как `confidence: low`.
- Сравнение — `jest-image-snapshot`; локально несовпадение видно в папке `__diff_output__`, обновление принятого снапшота — `yarn test:screenshots -u`.
- Запуск требует `docker` (см. файл). Если CI screenshot-чек не прошёл — это уже сигнал, дублировать его как finding не нужно, важнее разобраться, ожидаемо ли изменение.

## Реальный пример — visual hotfix со screenshot-тестом (`848edeea3`, `hotfix(slider)`)

PR чинит регресс выравнивания крайних подписей (`min`/`max`) под `Slider`/`SliderInput`. Показательные детали:

- **Changeset** (`patch` для обоих пакетов) описывает именно регресс, а не абстрактное "fix css": `Исправлен регресс выравниваний крайних подписей (min/max) под слайдером.`
- CSS-фикс заменяет часть magic-number координат на переменные/`calc()` (`top: -12px` → `top: var(--gap-12-neg)`), но главное — PR **добавляет новые screenshot-тесты**, целенаправленно нацеленные на именно сломанный сценарий (`describe('Slider | edge labels alignment', ...)`, `describe('SliderInput | edge labels alignment', ...)`), а не просто перегенерирует существующие снапшоты вслепую.

Это эталон для подобных visual-хотфиксов: исправление сопровождается тестом, который **доказывает** фикс и защищает от повторной регрессии именно этого сценария — а не только обновлением существующих снапшотов под новый результат рендера. Если visual-хотфикс обновляет существующие снапшоты, но не добавляет тест-кейс, покрывающий именно исправленный сценарий — это стоит отметить (не блокирующе, но как упущение).

## Severity

| Ситуация | Severity |
|---|---|
| В controlled-режиме компонент меняет видимое состояние в обход переданного prop (внутренний state дублирует/переопределяет controlled-prop) | **P1** |
| Callback (`onChange`/аналог) не вызывается в одном из режимов (controlled или uncontrolled) | **P1** |
| Комбинация состояний (`disabled`+`error`, `loading`+`disabled` и т.п.) не обработана и приводит к недоступному или сломанному интерфейсу | **P1**–**P2** в зависимости от частоты сценария |
| Обновлён `__image_snapshots__`-файл без сопутствующего изменения кода и без объяснения в PR/changeset | **P2** (нужно уточнение, не самостоятельный баг) |
| CSS/layout изменение без обновления/добавления screenshot-теста для затронутого сценария | **P2**–**P3** |
| Отсутствует состояние `empty`/`placeholder` там, где компонент явно может быть в этом состоянии | **P3** |
