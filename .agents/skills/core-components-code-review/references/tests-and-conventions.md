# Tests и project-specific conventions

## CI-авточеки

Реальные job'ы CI (`.github/workflows/main.yml`, `.github/workflows/changesets.yml`) на текущий момент:

| Job | Что проверяет | Как трактовать падение                                                                                                                |
|---|---|---------------------------------------------------------------------------------------------------------------------------------------|
| `lint` | `check-package-json` (сортировка package.json), `tsconfig check`, `format` (prettier), `lint` (`lint:css` + `lint:js` (ESLint, включая `jsx-a11y`) + `lint:deps` — **в т.ч. автоматически проверяет, что сторонняя зависимость объявлена и в корневом, и в локальном `package.json` пакета**) | Не дублируй как finding то, что уже упадёт здесь — code style, ESLint-нарушения, рассинхронизацию зависимостей.                       |
| `build` | Пакеты корректно собираются (`yarn build`) | Падение почти всегда указывает на реальную проблему в коде/типах, а не на случайный сбой.                                             |
| `test` | Unit/snapshot-тесты (`yarn test --coverage`) + сборка `themes` | Основной сигнал по unit-покрытию; смотри также локально, покрыто ли именно изменённое поведение, а не только факт прохождения.        |
| `screenshot-test` | Визуальные скриншот-тесты (`yarn test:screenshots` поверх собранной демки, с `git lfs`) | Падение = либо неотражённое обновление снапшота, либо непреднамеренная визуальная регрессия — см. `references/states-and-visual.md`.  |
| `search-vars` | Билд с `BUILD_WITHOUT_CSS_VARS`/`BUILD_MODERN_ONLY` + `yarn non-existent-css-vars` — поиск использования несуществующих CSS custom properties | Указывает на переменную, объявленную не там, откуда её импортируют (см. правило про `@import vars` ниже).                             |
| `changesets` | Прогоняет `yarn version-packages` над применёнными changeset-файлами | Косвенный сигнал по корректности формата changeset, не заменяет содержательную проверку типа bump'а (см. `references/public-api.md`). |
| `demo` / `deploy-pull-request-demo` | Storybook-демка собирается и деплоится для PR | Падение build'а демки — блокирующий сигнал, ссылка на демку должна появиться в PR.                                                    |

**Расхождение с `docs/code-review.stories.mdx`:** документ упоминает авточек "Lint PR / Validate PR title" — на момент этого ревью такого workflow/job в `.github/workflows/` не существует (проверено). Это конкретный, подтверждённый пример устаревания документа — не полагайся на точные названия джобов из него, свежий список смотри в `.github/workflows/` напрямую.

## Ручной анализ (из проектного чек-листа)

Помимо прохождения авточеков, `docs/code-review.stories.mdx` формулирует критерии ручного анализа — они остаются релевантным ориентиром независимо от точных названий CI-джобов:

- **Архитектура** — достаточно ли код разбит на модули, можно ли упростить без потери функциональности;
- **Функциональность** — соответствует ли изменение своей задаче, нет ли лишнего функционала (YAGNI);
- **Понятность** — не усложнён ли код без необходимости, есть ли комментарии в действительно сложных местах;
- **Тесты** — покрытие unit-тестами всех изменённых props, CSS-классов, рендера, основных функций компонента; скриншот-тесты для всех затронутых состояний и тем (не только для одного основного сценария);
- **Code style** — форматирование (учитывай, что prettier не всегда отрабатывает автоматически, несмотря на `lint`-job).

## "Неочевидные правила" проекта

Правила, которые не всегда ловятся автотестами/CI (там, где ловятся — отмечено явно) — стоит проверять целенаправленно:

- **CSS-класс не должен называться `default`** (источник правила — `docs/code-review.stories.mdx`, раздел «Неочевидные правила»; сам механизм поломки в репозитории не задокументирован, поэтому доверяй правилу, но не деталям "почему") — ломает часть сборок в продуктах-потребителях. Автоматической проверки на это нет — искать в diff вручную (`.default`/`styles.default`/`className: 'default'`).
- **`index.module.css` компонента обязан импортировать `@import '@alfalab/core-components-vars/src/index.css';`** — без этого CSS-переменные в сборке не резолвятся. Частично перекрывается CI-джобом `search-vars` (несуществующие переменные будут пойманы), но при добавлении **нового** пакета/`index.module.css` стоит явно свериться, что импорт присутствует, а не полагаться только на CI.
- **Импорт других компонентов библиотеки — только через `@alfalab/core-components-x`, не относительным путём.** Автоимпорт в IDE иногда подставляет `../component/src` — ESLint это не ловит (нет соответствующего `no-restricted-imports`-правила), проверка ручная.
- **Скриншоты обязаны сохраняться через git-lfs.** Если у автора PR не настроен `git-lfs` локально, снапшот уйдёт в обычный git. Проверяется просто: в diff `.png`-файл из `__image_snapshots__/` должен выглядеть как несколько строк текста (`oid sha256:...`, `size ...`), а не как обычный бинарный diff — второе означает, что git-lfs не сработал, и это finding.
- **В `*.stories.tsx` компоненты для сторис импортируются из собранного `@alfalab/core-components-x`, а не из `./Component`.** Исключение — относительный импорт специально для `<ArgsTable of={ComponentName}>`. Нужно, чтобы Storybook на gh-pages собирался из rollup-сборки, а не из исходников.

## Соответствие чек-листу автора PR (`.github/pull_request_template.md`)

Из пунктов шаблона агенту доступны для проверки только те, что видны в самом репозитории/diff/описании PR:

- осмысленное conventional-commit название PR (`feat(...)`/`fix(...)`) — соответствует ли фактическому характеру изменений (см. также `references/public-api.md` про соответствие типа изменения changeset'у);
- код покрыт тестами (см. выше);
- новые/изменённые props отражены в демках (`*.stories.tsx`) и документации (`*.docs.mdx`/`description.mdx`);
- changeset приложен (см. `references/public-api.md`);
- при визуальных изменениях — изображение было/стало в описании PR (это критерий полноты PR, не качества кода — при отсутствии стоит отметить как замечание к оформлению, не как code-issue).

## Severity

| Ситуация | Severity |
|---|---|
| CSS-класс назван `default` | **P1** (ломает сборки в продуктах-потребителях) |
| В `index.module.css` нового компонента отсутствует `@import vars` | **P1** |
| Относительный импорт другого library-компонента вместо `@alfalab/*` | **P2** |
| Изменённое поведение не покрыто unit- или screenshot-тестом | **P2** (P1, если это основной сценарий компонента) |
| Импорт в `*.stories.tsx` не из собранного пакета (кроме `ArgsTable`-исключения) | **P3** |
| Новая сторонняя зависимость не отражена в `package.json` пакета/root | не finding — уже ловится CI (`lint:deps`) |
| Отсутствует скриншот было/стало в описании PR при явных визуальных изменениях | **P3** (замечание к оформлению PR) |
