# Accessibility и interaction

## Базовые принципы (из `docs/accessibility.stories.mdx`)

- **Семантика прежде ARIA.** Нативный элемент с встроенным поведением (`<button>`, `<a>`, `<nav>`, `<label>`) предпочтительнее `<div role="...">`. Если в diff кликабельный/интерактивный элемент реализован через `div`/`span` вместо нативного тега без веской причины (например, кастомная верстка, несовместимая с `<button>`) — это finding.
- **Не переопределяй ARIA-ролью поведение семантического элемента** (`<h1 role="button">` вместо `<button><h1>...`). Если diff добавляет `role`, который меняет ожидаемое поведение нативного тега — finding.
- **Кастомный интерактивный элемент должен быть полноценно реализован, а не только визуально похож.** Если компонент рендерит `div` в роли кнопки/поля, проверь, что для него реализованы: клик мышью, активация `Enter`/`Space`, попадание в таб-порядок (`tabIndex`), видимый фокус. ARIA-роль сама по себе не даёт поведения — она только декларирует его для AT (assistive technology), реализация — на разработчике.
- **Интерактивные элементы должны иметь доступное имя/описание** — `aria-label`/`aria-labelledby`/связанный `<label>`, а не только `placeholder` (placeholder не читается частью скринридеров надёжно и исчезает при вводе).

## ESLint `jsx-a11y`

Проект подключает `jsx-a11y` не напрямую, а через `airbnb` в `@alfalab/lint-preset/eslint` — это по сути весь `plugin:jsx-a11y/recommended` набор правил (статические проверки разметки: `alt` у изображений, связь `label` с контролом, валидность `aria-*` и т.п.), с несколькими точечными переопределениями под конвенции проекта. Точный список правил и их настроек здесь намеренно не приведён — пресет может обновиться и список устареет. Если для оценки finding'а важно понять, поймает ли его линтер, проверь актуальную конфигурацию напрямую (`.eslintrc.cjs` и `node_modules/@alfalab/lint-preset/eslint/index.js`).

Важный нюанс, который стабилен архитектурно (не зависит от конкретного набора правил): в `.eslintrc.cjs` `ignorePatterns` исключает `**/*.test.*` и `**/*.stories.*` — значит `jsx-a11y` **не проверяет** Storybook stories и тестовые файлы, только код самого компонента (`Component.tsx`, `utils.ts` и т.п.).

Практическое следствие для ревью: если Lint-чек в CI прошёл, то очевидные статические проблемы разметки в коде компонента (не в stories/tests) уже отсеяны — не дублируй их как finding без дополнительной причины. Фокусируйся на том, что статический линтер принципиально не может поймать: **семантику взаимодействия** (описано в разделах ниже), а не только структуру разметки. В `.stories.tsx`/`.test.tsx` линтер a11y вообще не проверяет — там ручная проверка остаётся единственной линией защиты.

Формального a11y-тестирования (`jest-axe`/`axe-core` в тестах) в проекте нет — автоматизированного рантайм-контроля accessibility, кроме статического линта, не существует. Это поднимает значимость ручной проверки для любого PR, меняющего интерактивную разметку.

## Live-регионы для screen reader (паттерн `aria-live`)

Для объявления динамических изменений состояния (например, прогресс ввода) проект использует паттерн из `pass-code` (`feat(pass-code): добавить поддержку доступности`, `2a874b2b8`):

```tsx
<div role='status' aria-live='polite' aria-atomic='true' className={styles.visuallyHidden}>
    <span key={liveMessage.id}>{liveMessage.text}</span>
</div>
```

```ts
export function getAnnouncementText(currentLength: number, maxLength: number) {
    return currentLength >= maxLength
        ? 'Код введён полностью'
        : `Введено символов: ${currentLength}`;
}
```

Ключевые детали паттерна, на которые стоит смотреть при ревью похожих изменений:

- `role='status'` + `aria-live='polite'` — для некритичных обновлений (не прерывает текущую речь скринридера); `aria-live='assertive'`/`role='alert'` уместны только для срочных сообщений (ошибки валидации), не для рутинного прогресса;
- `aria-atomic='true'` — регион озвучивается целиком при каждом изменении, а не только изменённая часть;
- `key={liveMessage.id}` на дочернем `<span>` — важный нюанс: если текст объявления не меняется между двумя обновлениями (например, дважды подряд "Введено символов: 3" из-за особенностей ввода), простое изменение `textContent` может не быть замечено скринридером; инкрементирующийся `key` форсирует remount и гарантирует повторное озвучивание;
- визуально скрыт через миксин `visually-hidden` из `packages/vars/src/mixins.css` (`@define-mixin visually-hidden`, стандартный clip-hack), а не `display: none`/`visibility: hidden` — те исключили бы элемент из accessibility tree.

Если PR добавляет новый live-статус (progress, счётчик, async-результат) без этого паттерна (или без `visually-hidden`, скрывая его `display: none`) — это finding.

## Keyboard-only фокус для кастомных интерактивных элементов

Core-компоненты уже имеют стилизованный keyboard-only фокус "из коробки". Для **кастомных** интерактивных элементов (внутри библиотеки — например, там, где готового Core-компонента нет и верстается свой) проект использует `packages/keyboard-focusable` — компонент `KeyboardFocusable` (рендер-проп) поверх `useFocus(ref, 'keyboard')` из `@alfalab/hooks`, уже применяемый, например, в `tabs` и `attach`. Если diff добавляет новый кастомный интерактивный элемент со своей focus-стилизацией вместо переиспользования этого паттерна — не обязательно blocking, но стоит отметить как P2/P3 (несогласованность с существующим подходом), если это по факту приводит к тому, что фокус виден и при клике мышью (что прямо запрещено гайдом `docs/keyboard.stories.mdx`: "не скрывайте фокус... стилизуйте так, чтобы он был виден только при управлении с клавиатуры").

`outline: none`/`tabIndex={-1}` на интерактивном элементе без эквивалентной замены (кастомного focus-индикатора или намеренного исключения из таб-порядка с объяснением) — почти всегда finding.

## Keyboard / focus / pointer чек-лист

Для затронутых PR-ом интерактивных сценариев проверяй симметрию между способами взаимодействия — то, что работает мышью, должно работать и с клавиатуры, и наоборот:

**Keyboard:**
- `Tab`/`Shift+Tab` — логичный порядок обхода (слева направо, сверху вниз), не нарушенный новым/переставленным элементом;
- `Enter`/`Space` — активируют кастомные интерактивные элементы так же, как нативную кнопку;
- `Escape` — закрывает диалоги/попапы/меню, если они открыты;
- `Arrow keys`/`Home`/`End` — навигация в составных виджетах (табы, меню, списки с выбором), если компонент такую навигацию подразумевает;
- новый интерактивный элемент не выпадает из таб-порядка (`tabIndex` не потерян/не выставлен в `-1` без причины).

**Focus:**
- получение и видимость фокуса (focus ring) на новом/изменённом интерактивном элементе;
- **focus trap** — для модалок/диалогов фокус не должен уходить за пределы открытого окна;
- **focus restoration** — после закрытия диалога/попапа фокус возвращается на элемент, который его открыл (типичный regression: добавили новый способ закрытия — например, клик по backdrop — и забыли про restoration для него);
- изменение DOM-структуры/порядка рендера не должно молча сдвигать focus order.

**Pointer:**
- `click`/`outside click` — если добавляется новый способ взаимодействия (например, клик вне компонента закрывает попап), у него должен быть keyboard-эквивалент (`Escape`), а не только pointer;
- `hover`-only функциональность (тултип, раскрытие по наведению) должна быть доступна и без hover (фокус клавиатурой либо клик) — иначе недоступна на touch-устройствах и с клавиатуры.

## Severity

| Ситуация | Severity |
|---|---|
| Кастомный интерактивный элемент не реагирует на `Enter`/`Space`, недоступен с клавиатуры | **P1** (основной сценарий недоступен с клавиатуры) |
| Focus trap/restoration сломан в диалоге/попапе основного сценария | **P1** |
| `outline: none` добавлен без замены focus-индикатора | **P2**–**P1** в зависимости от того, насколько часто используется компонент |
| Новый live-статус без `aria-live`/`visually-hidden` паттерна | **P2** |
| ARIA-роль меняет поведение нативного элемента без реализации соответствующей семантики | **P1** |
| Отсутствие доступного имени (`label`/`aria-label`) у нового интерактивного поля | **P2** |
| Несогласованность focus-стилизации с существующим `KeyboardFocusable`-паттерном, но фокус корректно виден только при клавиатуре | **P3** |
| ESLint-правило `jsx-a11y/*` настроено в проектном конфиге как `warn`, а не `error` | не blocking сам по себе — это осознанная настройка проекта, а не пропущенная проблема |
